# Deploy GoRent with Render and Vercel

The backend is Django on Render. The frontend is a static Vercel project built from `frontend/`. Both use the existing GoRent Supabase PostgreSQL project. Do not create or attach a second database.

## 1. Render backend

1. Connect this GitHub repository in Render. Select **Blueprints → New Blueprint Instance** and use the root `render.yaml`. It creates one free Python web service named `gorent-backend-ratneshgf`.
2. Enter the secrets requested by Render's Blueprint form:
   - `DATABASE_URL`: the **GoRent** Supabase Session pooler URI (port 5432) with URL-encoded password and `sslmode=require`.
   - `CLOUDINARY_URL`: the existing Cloudinary URL for car photos.
   - `CORS_ALLOWED_ORIGINS`: the exact Vercel production origin, such as `https://your-project.vercel.app`. If Vercel has not assigned it yet, set a temporary HTTPS origin, then replace it in Render once Vercel is deployed.
   - `SECRET_KEY` is generated by Render. `SUPABASE_PROJECT_REF` is set in the Blueprint and must match the URI.
3. Wait for the build and deployment. The build installs dependencies and collects static assets. On startup, Django applies migrations before Gunicorn starts. Verify `https://<render-host>/api/health/` returns `{"status":"ok"}`.
4. Render supplies its own hostname through `RENDER_EXTERNAL_HOSTNAME`; Django trusts only that hostname plus configured local hosts. `DEBUG=0` and HTTPS proxy settings are enabled.

## 2. Vercel frontend

1. Import the same GitHub repository into Vercel as a **new project**.
2. Set **Root Directory** to `frontend`. The committed `vercel.json` runs `node build.mjs` and serves `dist`.
3. Add build environment variable `GORENT_API_BASE=https://<render-host>` (origin only, no `/api` or trailing path). Deploy.
4. Copy the assigned Vercel production origin into Render's `CORS_ALLOWED_ORIGINS` and redeploy the Render service. If you use a custom Vercel domain, add that exact origin too, separated by a comma.
5. Confirm the Vercel home page loads and its `/api/vehicles` browser request goes to Render without a CORS error. Register and sign in through Vercel; the API persists records in Supabase.

The frontend build rejects an empty or non-HTTPS API origin. Local Django preview still uses same-origin `/api/` calls through `frontend/config.js`.

## 3. Private ID documents and owner upload

Render's free filesystem is temporary, so production uploads use the `PrivateDocument` table in Supabase. ID files have no public URL and are served only by authenticated Django endpoints. The database storage migration is included in the code.

Migration `0015` adds renter account ID fields. Render runs migrations on startup. Saved renter IDs persist across login sessions; each booking receives its own private copy. Only the owner of that booking can open the copy through the authenticated document endpoint. Owner ID files have no renter-facing endpoint.

The four existing GoRent ID files were copied into its private Supabase database table with the user's explicit approval and verified byte for byte. The local copies remain in `private_media/` and are not committed to Git. If more documents are uploaded through the local preview before production deployment, run `python manage.py migrate_private_documents` to check the pending count, then run it with `--execute` after confirming those documents may be transferred.

An owner can submit a government, student, employee or other ID to unlock listing. The app checks file type and size, stores the file privately, and records `submitted`; it does not authenticate the document or claim the owner is verified. Existing local `demo_checked` records do not unlock production listing. Owners with that status should upload again on the live site.

Keep `DATABASE_URL`, `CLOUDINARY_URL` and any provider secrets in Render environment variables, never GitHub or Vercel frontend settings. The Vercel build gets only the public Render origin.
